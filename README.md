# d8a-de-workbench

The local data platform of the D8A Academy Data Engineering path. One `docker compose` file, one `make up`, one `make check` that prints green. Every project from P2 on starts from this repository (use it as a GitHub template: "Use this template" on GitHub, or copy the folder).

This is the template repository the D8A Data Engineering path links to. Start a project with **Use this template** on GitHub, then clone your copy.

## What is in the box

| Service | Profile | What it is | Port |
|---|---|---|---|
| `postgres` | always | PostgreSQL 16, database `warehouse`, schemas `raw`, `staging`, `marts` (your warehouse) and `app` (the source system of the app context, loaded from CSV) | 5432 |
| `dbt` | always (run on demand) | dbt-postgres 1.8, project in `./dbt` | |
| `sources` | `app`, `finance`, `marketing`, `operations` | One simulated source system per data context (see below) | 8080 (marketing API) |
| `airflow-*` | `airflow` | Airflow 2.9 (webserver, scheduler, its own metadata database), DAGs in `./airflow/dags`, dbt installed in the image | 8081 |
| `redpanda`, `redpanda-console` | `redpanda` | A Kafka-compatible broker that runs on a laptop, with a console | 9092, 8082 |
| `minio`, `minio-init` | `minio` | S3-compatible object store with a `lake` bucket, the parquet lake of the operations context | 9000, 9001 |

Profiles keep your laptop usable: Airflow needs about 4 GB of RAM, Spark in local mode about the same, Redpanda is light. Start only what the project you are on needs.

## Start

```bash
cp .env.example .env            # once; the defaults work
make data CONTEXT=app           # download the company's source tables for your context (app | finance | marketing | operations)
make up CONTEXT=app             # postgres + the app's simulated source system
make check                      # prints what runs and what it holds; everything green = ready
```

Project 4 adds `PROFILE=airflow`, Project 5 adds `redpanda` (app) or `minio` (operations):

```bash
make up CONTEXT=app PROFILE=airflow
make up CONTEXT=app PROFILE="airflow redpanda"
```

`make down` stops everything and keeps the data; `make reset` stops everything and deletes the volumes.

## The simulated source systems

They are the heart of the workbench: your pipeline reads from a system that behaves like production, not from a CSV you downloaded once. All four are standard-library Python, seeded, and print their reference counts with `--stats` so a test can know what to expect.

| Context | Simulator | What it does | What breaks on purpose |
|---|---|---|---|
| app | `sources/app_events.py` | Publishes the shop's app events as JSON lines (files under `data/app_events/`, and to the Kafka topic `app.events` when Redpanda is up) | At least once: 3% of events are sent twice (same `event_id`). 2% arrive up to two hours late, out of order. App version 2 renames `value` to `amount` and adds `currency`. 0.4% of product ids are not in the catalogue. |
| finance | `sources/eod_files.py` | Drops the core system's end-of-day files at 02:00 (or now, with `--now`): `transactions_YYYYMMDD.csv`, `ledger_YYYYMMDD.csv` and a `control_YYYYMMDD.json` with row counts, totals and checksums, under `data/eod/incoming/` | One day in ten arrives 45 minutes late. One in fifty is corrupted (truncated last row, control total off). About every twenty days a `_v2` file restates a previous day. Twelve ledger entries per quarter are off by a cent. |
| marketing | `sources/saas_api.py` | A REST API on port 8080 with six paginated endpoints (ads campaigns and spend, CRM leads and contacts, email sends, analytics sessions) behind a bearer token, with cursors | A 429 with `Retry-After` every 300 calls. From 2024-07-01 the spend endpoint renames `spend` to `cost`. Cursors expire after 10 minutes. Some campaign ids in spend do not exist in campaigns. |
| operations | `sources/telemetry.py` | Writes the fleet's telemetry (400 vehicles, one reading every 10 seconds) as partitioned parquet (or gzip CSV without pyarrow) under `data/lake/telemetry/dt=YYYY-MM-DD/hour=HH/`, and uploads to MinIO when it is up | Gaps of five minutes on some vehicles, one vehicle whose GPS is frozen, one whose speed sensor reports 300 km/h, 1% duplicate readings, a partition rewritten an hour later. |

Reference counts for every simulator, per day and seed, are in the d8a.academy repository under `scripts/datasets/reference/de_<context>.json` (section `simulator`), generated by running each simulator with `--stats`.

## Layout of a project repository built from this template

```
your-project/
├── docker-compose.yml        the workbench, as is (P4 asks you to write your own)
├── Makefile
├── .env.example
├── sources/                  the simulators (do not edit; your pipeline reads from them)
├── pipeline/                 your Python (P2: extract, load, validate)
├── tests/                    your pytest tests
├── dbt/                      your dbt project (P3)
├── airflow/dags/             your DAGs (P4)
├── adr/                      your architecture decision records (P5, P6)
├── .github/workflows/ci.yml  lint, tests, dbt parse on every push
└── README.md                 how to run, what runs, decisions, interview script
```

## Warehouse

The warehouse of P3 and P5 is your choice: PostgreSQL in this Compose (default), DuckDB (local file, `dbt-duckdb`), BigQuery sandbox or Snowflake trial. `dbt/profiles.yml` has a target for each; the content shows the steps for the one you picked.

## Requirements

Docker Desktop (or Docker Engine with the compose plugin) 24 or later, 8 GB of RAM (16 GB to run Airflow and Spark at the same time), `make`, `curl`, Python 3.10 or later for running the simulators or tests outside Docker.
